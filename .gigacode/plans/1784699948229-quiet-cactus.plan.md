# План исправления архитектурных нарушений валидации - ЗАВЕРШЕН

## Проблемы

### 1. Jakarta Validation в application.dto
- `AssetCreateRequest` содержит `@NotNull` (архитектурное нарушение)
- `AssetUpdateRequest` не содержит валидационных аннотаций

### 2. DTO зависят от domain enums
- Web DTO используют `AssetType` и `AssetCriticality` напрямую
- Это создаёт риск breaking changes при изменении domain enums

## Решение

### Шаг 1: Создать web DTO с валидацией ✅

**Файл:** `infrastructure/web/dto/AssetCreateRequest.java` ✅
**Файл:** `infrastructure/web/dto/AssetUpdateRequest.java` ✅

### Шаг 2: Обновить application DTO (без валидации) ✅

**Файл:** `application/dto/AssetCreateRequest.java` - обновлён без валидации
**Файл:** `application/dto/AssetUpdateRequest.java` - обновлён без валидации

### Шаг 3: Обновить application service ✅

**Файл:** `application/service/AssetService.java`
- Добавлены методы конвертации String → enums
- `parseAssetType()`
- `parseAssetCriticality()`
- `parseAssetStatus()`

### Шаг 4: Обновить controller ✅

**Файл:** `infrastructure/web/AssetController.java`
- Импортированы web DTO из `infrastructure.web.dto`

### Шаг 5: Обновить тесты ✅

**Файл:** `src/test/java/com/powerassetintelligence/unit/AssetServiceTest.java`
**Файл:** `src/test/java/com/powerassetintelligence/integration/api/AssetControllerMockMvcIT.java`

## Результат

✅ Все тесты прошли успешно (33 tests, 0 failures)
✅ Сборка успешна
✅ Jakarta Validation перенесён в infrastructure layer
✅ Web DTO используют String вместо domain enums
✅ Application layer больше не зависит от web-фреймворков

## Резюме изменений

### Архитектурное нарушение исправлено
- Jakarta Validation перенесён из `application.dto` в `infrastructure.web.dto`
- Application layer больше не зависит от web-фреймворков

### Стратегия валидации
- **Web DTO** (`infrastructure.web.dto`) - содержат валидационные аннотации с String
- **Domain DTO** (`application.dto`) - без валидации, с domain enums
- **Application Service** - конвертирует String → enums

### Преимущества
1. ✅ Соблюдение Clean Architecture принципов
2. ✅ Меньше риск breaking changes при изменении domain enums
3. ✅ Валидация происходит на границе web слоя
4. ✅ Application service может быть переиспользован для CLI/Kafka интерфейсов
